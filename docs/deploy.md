# Deploying the free demo (Day 17)

Five free accounts, in this order. Each step says what to click, what to copy and how to check it. Secrets go only into each provider's settings or your local `.env.neon` (git ignores it); never paste them into chat or commit them.

```
phone ──► Cloudflare Pages (web app + /api proxy) ──► Render (NestJS API + worker) ──► Neon (PostgreSQL)
                                                          └──► Brevo (login code emails)
UptimeRobot ──► Render /health every 5–10 min (keeps the API awake; never touches the database)
```

Why the proxy: the web app and the API must look like one site to the browser, or the refresh cookie (`SameSite=Strict`) is never sent and iPhones block it. `apps/web/functions/[[path]].ts` forwards `/api/*` and `/health` to Render and nothing else.

UIs change; if a button has moved, look for the same words nearby. Free-tier limits change too: check each pricing page once before you rely on it.

## 0. Push to GitHub

Render and Cloudflare deploy from GitHub `main`. Push the latest commits first:

```bash
git push origin main
```

## 1. Brevo (login code emails) — about 10 minutes

1. Sign up at brevo.com (free plan). Skip the marketing set-up questions.
2. **Verify a sender:** top-right menu → **Senders, Domains & Dedicated IPs** → **Senders** → **Add a sender**. Use an address you own (Gmail works). Open the confirmation email and click the link.
3. **API key:** top-right menu → **SMTP & API** → **API Keys** → **Generate a new API key**, name it `dafter-render`. Copy it once; Brevo won't show it again.
4. Keep these two for step 3: `BREVO_API_KEY` (the key) and `MAIL_FROM` (the verified sender address).

Check: the sender shows as **Verified**.

## 2. Neon (database) — about 10 minutes

1. Sign up at neon.tech (free plan) → **New project**.
   - Name: `dafter` · PostgreSQL version: **17** · Region: **AWS Europe (Frankfurt)** (closest to Egypt, and next to Render's Frankfurt region).
2. On the project dashboard, click **Connect**. You need two connection strings:
   - **Pooled:** with **Connection pooling** on (the host contains `-pooler`). This is `DATABASE_URL`.
   - **Direct:** with **Connection pooling** off. This is `DATABASE_URL_UNPOOLED` (migrations and pg-boss use it).
   Both should end in `?sslmode=require`.
3. In the repo root, create `.env.neon` (git ignores `.env.*`). Either with the Neon CLI (`npm i -g neon`, then `neon login`; the project is linked in the git-ignored `.neon` file):

   ```bash
   neon env pull --file .env.neon -e DATABASE_URL -e DATABASE_URL_UNPOOLED
   ```

   Always pass `--file .env.neon`: without it the CLI writes into your existing `.env` and points local development at Neon. Or by hand:

   ```
   DATABASE_URL=<pooled string>
   DATABASE_URL_UNPOOLED=<direct string>
   ```

4. Migrate and load the demo data (Arabic names, 3 groups, 12 students, 2 past weeks of attendance):

   ```bash
   pnpm demo:seed:neon
   ```

Check: it prints `Seeded the demo center…`. Running it again prints `Demo data already there`.
If it fails with `permission denied to create role` or a `pg_trgm` error, stop and send me the error line (no connection string).

## 3. Render (API and worker) — about 15 minutes

1. Sign up at render.com with GitHub, and allow it to see the `Dafter` repo.
2. **New** → **Blueprint** → pick the `Dafter` repo. Render reads `render.yaml` and shows one service, `dafter-api` (free, Frankfurt).
3. Fill in the four secrets it asks for:
   - `DATABASE_URL`: Neon pooled string
   - `DATABASE_URL_UNPOOLED`: Neon direct string
   - `BREVO_API_KEY` and `MAIL_FROM`: from step 1
   `JWT_SECRET` and `QR_SECRET` are generated by Render; leave them.
4. **Apply**. The first build takes about 5 minutes. The log should end with `Migrations Applied`, `Worker started` and `Nest application successfully started`.
5. Copy the service URL from the top of the page, e.g. `https://dafter-api.onrender.com` (the name may have a suffix if taken).

Check: open `<render URL>/health` → `{"status":"ok"}`.
Never add `DEV_MAIL_INBOX` here: it shows login codes to anyone.

## 4. Cloudflare Pages (web app) — about 15 minutes

1. Sign up at dash.cloudflare.com → **Workers & Pages** → **Create** → the **Pages** tab → **Connect to Git** → pick the `Dafter` repo. (If it only offers Workers, look for "Looking to deploy Pages? Get started".)
2. Build settings:
   - Project name: `dafter` (the URL becomes `dafter.pages.dev`, or with a suffix)
   - Production branch: `main`
   - Framework preset: **None**
   - Root directory: `apps/web`
   - Build command: `cd ../.. && npx --yes pnpm@11.5.1 install --frozen-lockfile && npx --yes pnpm@11.5.1 turbo run build --filter=@dafter/web`
   - Build output directory: `dist`
3. Environment variables (Production):
   - `NODE_VERSION` = `22`
   - `SKIP_DEPENDENCY_INSTALL` = `1` (the build command installs with pnpm itself)
   - `API_ORIGIN` = your Render URL from step 3, with no trailing slash
4. **Save and Deploy**. If `API_ORIGIN` was added after the first deploy, go to **Deployments** → **Retry deployment**, because Functions read variables at deploy time.

Check, all on the Pages URL:
- `/health` → `{"status":"ok"}` (this goes through the proxy to Render)
- `/login` shows the Arabic login page; sign in as `01000000002` / `dafter-dev-123`, pick سنتر النور, reload: you stay signed in (the cookie works).

## 5. UptimeRobot (keeps Render awake) — about 5 minutes

1. Sign up at uptimerobot.com (free) → **New monitor**.
2. Type **HTTP(s)**, URL `<render URL>/health`, interval **5 minutes** (the free minimum; anything under 15 keeps Render awake).
3. Save.

Check: the monitor turns green. `/health` never touches the database, so Neon still sleeps when nobody uses the app (its first query after a pause takes about half a second).

## 6. Live smoke test

From the repo root, against the Pages URL:

```bash
E2E_BASE_URL=https://dafter.pages.dev pnpm e2e:live
```

In PowerShell: `$env:E2E_BASE_URL='https://dafter.pages.dev'; pnpm e2e:live`.
It runs only the sign-in and workspace-switch test (it changes no data), in Arabic and English. Run it after every deploy.

## 7. By hand, once, on real phones

These can't be automated (see `docs/known-limits.md`):

- **Android (Chrome):** open an invite link from the student page → Install → in the installed app, log in with the emailed code → bind → scan the teacher's QR from a laptop screen.
- **iPhone (Safari):** the same, using **Share → Add to Home Screen**, then paste the invite link inside the installed app.
- The teacher's live QR screen on a laptop: rotates every 10 seconds, the check-in appears at once.
- Close the session: the absence shows on `/dev/phone` within a minute (or at 08:00 Cairo during quiet hours).

## Demo accounts and resetting the data

- Owner `01000000001`, teacher `01000000002`, assistant `01000000003`, password `dafter-dev-123`. Anyone with the link can sign in: it's a demo, never real data.
- To reset: Neon → **SQL Editor** → run `DROP SCHEMA public CASCADE; CREATE SCHEMA public; DROP SCHEMA IF EXISTS drizzle CASCADE; DROP SCHEMA IF EXISTS pgboss CASCADE;` → then `pnpm demo:seed:neon` → then Render → **Manual Deploy** → **Restart service**.

## Troubleshooting

| Symptom | Likely cause | Fix |
|:--|:--|:--|
| Render build fails at `pnpm install` | Lockfile out of date | Run `pnpm install` locally, commit `pnpm-lock.yaml`, push |
| Render log: `DATABASE_URL is not set` | Secret missing | Render → Environment → add it → Save (redeploys) |
| Render log: `MAIL_PROVIDER=brevo needs…` | Brevo secrets missing | Add `BREVO_API_KEY` and `MAIL_FROM` |
| Pages `/health` returns 404 or HTML | `_routes.json` or the Function wasn't deployed | Check the build log lists `functions/[[path]].ts`; check root directory is `apps/web` |
| Pages `/health` returns 500 | `API_ORIGIN` missing or wrong | Set it (no trailing slash) and retry the deployment |
| Signed out after every reload | The app was opened on the Render URL, not the Pages URL | Always use the Pages URL |
| First request takes ~50 s | Render was asleep | Check the UptimeRobot monitor is running |
| Login code email never arrives | Sender not verified, or the free daily limit reached | Brevo → Transactional → Logs |
